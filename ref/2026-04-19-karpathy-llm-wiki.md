# LLM Wiki — Andrej Karpathy (原文)

## 核心思想

大多数人的 LLM + 文档使用体验是 RAG：上传文件 → LLM 检索相关片段 → 生成回答。问题在于：LLM 每次都从零重新发现知识，没有积累。

**卡帕西的方案不同：**

不是只在查询时从原始文档检索，LLM 会**增量构建和维护一个持久化的 wiki**——一个结构化的、带交叉链接的 Markdown 文件集合，介于你和原始资料之间。

当你添加新资料时，LLM 不会只索引它待以后检索。它会读取它，提取关键信息，将其**整合到现有 wiki 中**——更新实体页面、修订主题摘要、标注新旧数据矛盾的地方、强化或挑战正在演变的综合理解。

知识是**编译一次，然后保持最新**，不是每次查询都重新派生。

> 关键差异：wiki 是一个**持久的、复合的产物**。交叉引用已经在那里了。矛盾已经被标注了。综合理解已经反映了你所阅读的一切。wiki 随你添加的每一条资料和每一个问题而变得越来越丰富。

## 三层架构

### 第一层：Raw Sources（原始资料）
- 你的文档集合：论文、文章、图片、数据文件
- **不可变**——LLM 只读，不修改
- 这是你的 source of truth

### 第二层：Wiki（LLM 生成的知识库）
- LLM 生成的 Markdown 文件目录
- 摘要页、实体页、概念页、对比页、综述页
- LLM 完全拥有这一层
- 创建页面、当新资料到达时更新、维护交叉引用、保持一切一致

### 第三层：Schema（规范层）
- 一个文档（如 Claude Code 的 CLAUDE.md）
- 告诉 LLM wiki 是如何构建的、有哪些约定、在摄入资料、回答问题或维护 wiki 时遵循什么工作流
- 这是关键配置文件——它使 LLM 成为有纪律的 wiki 维护者而不是通用聊天机器人

## 操作

### Ingest（摄入）
把新资料丢进 raw 目录 → 告诉 LLM 处理它
- LLM 读取资料
- 与你讨论关键要点
- 在 wiki 中写摘要页
- 更新 index
- 更新相关实体和概念页面
- 追加条目到 log

单一资料可能涉及 10-15 个 wiki 页面。

### Query（查询）
向 wiki 提问
- LLM 搜索相关页面
- 读取并综合回答
- 引用来源
- 好答案可以**归档回 wiki** 作为新页面

### Lint（检查）
定期让 LLM 做健康检查：
- 页面间的矛盾
- 被新资料取代的不新鲜声明
- 没有入站链接的孤立页面
- 被提及但缺乏独立页面的重要概念
- 缺失的交叉引用
- 可以通过网络搜索填补的数据空白

## 索引和日志

### index.md（内容导向）
- wiki 的目录
- 每个页面一行：链接 + 一句话摘要 + 可选元数据
- 按类别组织（实体、概念、来源等）
- LLM 在每次 ingest 时更新
- 回答问题时，LLM 先读 index 找到相关页面，再深入

### log.md（时间导向）
- 追加记录：发生了什么、何时发生
- 格式：`## [2026-04-02] ingest | Article Title`
- 用简单 unix 工具可解析：`grep "^## \[" log.md | tail -5`

## 为什么有效

维护知识库繁琐的部分不是阅读或思考——而是**簿记**。更新交叉引用、保持摘要最新、标注新旧数据矛盾、在数十个页面间保持一致。人类放弃 wiki 是因为维护负担增长比价值更快。LLM 不会厌倦、不会忘记更新交叉引用、可以一次更新 15 个文件。

**人类的工作是：** 管理来源、指导分析、问好问题、思考一切意味着什么。
**LLM 的工作是：** 其他一切。

> 这是范式转变：LLM 是编译器，原始资料是源代码，生成的 Wiki 是可执行文件。
